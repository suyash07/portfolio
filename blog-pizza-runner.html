Section A: Pizza Metrics

10 questions covering order volumes, customer behaviour, and delivery filtering. The main challenge: the raw data has inconsistent nulls — the string 'null' mixed with actual SQL NULL, and dirty whitespace. Every query that touches runner_orders needs a filter to exclude cancelled orders.

A1 How many pizzas were ordered?

A direct row count on customer_orders — each row is one pizza ordered, regardless of cancellation.

SQL A1
SELECT COUNT(*) FROM customer_orders;
count
14

A2 How many unique customer orders?

Orders, not pizzas. Multiple pizzas can share an order_id, so we use DISTINCT.

SQL A2
SELECT COUNT(DISTINCT order_id) FROM customer_orders;
count
10

A3 Successful deliveries per runner

The dataset stores cancelled orders as the string 'null' in the duration column — not a real SQL NULL. Filtering WHERE duration <> 'null' catches this.

SQL A3
SELECT
    runner_id,
    COUNT(*) AS successful_orders
FROM (
    SELECT * FROM runner_orders
    WHERE duration <> 'null'
) AS sub
GROUP BY 1;

Dirty data alert: This dataset mixes actual SQL NULLs with the string 'null' and blank strings for missing values. Every section requires careful null handling before any meaningful aggregation.

A4 Pizza type breakdown — delivered only

Join three tables, filter to delivered orders, count by pizza name.

SQL A4
WITH delivered_pizzas AS (
    SELECT
        cust.pizza_id,
        pizza.pizza_name
    FROM customer_orders AS cust
    LEFT JOIN runner_orders AS runna
        ON cust.order_id = runna.order_id
    JOIN pizza_names AS pizza
        ON cust.pizza_id = pizza.pizza_id
    WHERE runna.distance <> 'null'
)
SELECT pizza_name, COUNT(*) FROM delivered_pizzas GROUP BY 1;

A5 Vegetarian vs Meatlovers per customer

Join customer_orders to pizza_names, then group by customer and pizza type. This includes undelivered orders — the question asks for "ordered", not "delivered".

SQL A5
WITH orders AS (
    SELECT cust.*, pizza.pizza_name
    FROM customer_orders AS cust
    JOIN pizza_names AS pizza
        ON cust.pizza_id = pizza.pizza_id
)
SELECT
    customer_id,
    pizza_name,
    COUNT(pizza_id) AS n_pizza
FROM orders
GROUP BY 1, 2
ORDER BY 1;

A6 Maximum pizzas in a single delivered order

Count pizzas per order (delivered only), sort descending, take the top row.

SQL A6
SELECT
    cust.order_id,
    COUNT(pizza_id) AS n_orders
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
WHERE duration != 'null'
GROUP BY 1
ORDER BY 2 DESC
LIMIT 1;

A7 Pizzas with changes vs no changes

This one requires careful null handling. Both an empty string ' ' and the string 'null' mean "no exclusions/extras" — we need to treat both as absent. Conditional aggregation via SUM(CASE WHEN ...) handles the per-customer split in one pass.

SQL A7
SELECT
    cust.customer_id,
    SUM(CASE WHEN
        exclusions <> ' ' OR extras <> ' '
        THEN 1 ELSE 0 END) AS at_least_one_change,
    SUM(CASE WHEN
        (exclusions = ' ' OR exclusions = 'null')
        AND (extras = ' ' OR extras = 'null')
        THEN 1 ELSE 0 END) AS no_change
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
WHERE distance != 'null'
GROUP BY 1;

Pattern: SUM(CASE WHEN condition THEN 1 ELSE 0 END) is a pivot-in-place — it lets you count multiple conditional buckets in a single query pass without a separate subquery per condition.

A8 Pizzas with both exclusions AND extras

Stricter version of A7 — both columns must be non-null and non-empty. Uses AND between the two conditions rather than OR.

SQL A8
SELECT COUNT(cust.order_id)
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
WHERE distance != 'null'
AND (exclusions != 'null' AND exclusions != '')
AND (extras != 'null'     AND extras != '');

A9 Order volume by hour of day

EXTRACT(HOUR FROM order_time) pulls the hour component from the timestamp, then we count orders per hour. Useful for spotting peak ordering windows.

SQL A9
SELECT
    EXTRACT(HOUR FROM order_time) AS hr_day,
    COUNT(order_id) AS n_orders
FROM customer_orders
GROUP BY 1
ORDER BY 1;

A10 Order volume by day of week

Two approaches: EXTRACT(DOW ...) returns a numeric 0–6 (Sunday = 0). TO_CHAR(..., 'DAY') returns the human-readable name — better for a report but harder to sort correctly.

SQL A10 — readable version
SELECT
    TO_CHAR(order_time, 'DAY') AS day_of_week,
    COUNT(order_id) AS n_orders
FROM customer_orders
GROUP BY 1
ORDER BY 1;

Section B: Runner & Customer Experience

7 questions focused on delivery operations — pickup times, distances, speeds, and success rates. This section required the most data cleaning: ALTER TABLE and UPDATE to strip non-numeric characters from duration and distance before any arithmetic was possible.

B1 Runners signed up per week

Week numbers are computed by subtracting a baseline date (2021-01-01) and dividing by 7. FLOOR gives the integer week bucket; +1 makes it 1-indexed.

SQL B1
SELECT
    FLOOR((registration_date - DATE '2021-01-01') / 7) + 1 AS registration_week,
    COUNT(*) AS runners
FROM runners
GROUP BY 1;

B2 Average runner pickup time

First the data had to be cleaned — duration stored values like '32 minutes' and 'null' strings. After stripping non-numeric characters with regexp_replace and casting to INTEGER, the pickup time was computed using EXTRACT(EPOCH FROM ...) to get seconds, then dividing by 60 for minutes.

SQL B2 — data cleaning
-- Strip non-numeric characters from duration
UPDATE runner_orders
SET duration = regexp_replace(duration, '[^0-9]', '', 'g')
WHERE duration != 'null';

UPDATE runner_orders SET duration = 0 WHERE duration IS NULL;

ALTER TABLE runner_orders
ALTER COLUMN duration TYPE INTEGER USING duration::INTEGER;
SQL B2 — average pickup time
SELECT
    runna.runner_id,
    ROUND(AVG(
        EXTRACT(EPOCH FROM
            (pickup_time::timestamp - order_time::timestamp)
        ) / 60
    )) AS avg_pick_time
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
WHERE duration <> 0
GROUP BY 1;

Datetime arithmetic: EXTRACT(EPOCH FROM (ts2 - ts1)) gives the difference in seconds — divide by 60 for minutes, 3600 for hours. Much cleaner than DATEDIFF equivalents in other databases.

B3 Does order size affect prep time?

Group orders by pizza count, then average the cook time (pickup − order time) per group. The CTE computes cook time at the order level; the outer query averages by pizza count.

SQL B3
WITH prep_time AS (
    SELECT
        cust.order_id,
        COUNT(cust.order_id) AS n_pizzas,
        EXTRACT(EPOCH FROM
            (pickup_time::timestamp - order_time::timestamp)
        ) / 60 AS cook_time
    FROM customer_orders AS cust
    JOIN runner_orders AS runna
        ON cust.order_id = runna.order_id
    WHERE duration <> 0
    GROUP BY 1, 3
)
SELECT
    n_pizzas,
    ROUND(AVG(cook_time)) AS avg_prep_time
FROM prep_time
GROUP BY 1;
n_pizzasavg_prep_time (mins)

329

Clear relationship: each additional pizza adds roughly 8–10 minutes of prep. This is useful operational data for setting customer delivery expectations.

B4 Average distance per customer

Similar cleaning needed on distance — values like '20km' and 'null'. After stripping and casting, values that were stored as integers (e.g. 200 instead of 20.0) were scaled back by dividing by 10.

SQL B4 — query
SELECT
    cust.customer_id,
    ROUND(AVG(runna.distance)) AS avg_distance_km
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
WHERE duration <> 0
GROUP BY 1;

B5 Longest vs shortest delivery difference

Simple MAX - MIN after filtering cancelled orders. Once the column is clean and typed as INTEGER, this is a one-liner.

SQL B5
SELECT
    MAX(runna.duration) - MIN(runna.duration) AS duration_diff
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
WHERE duration <> 0;

B6 Average speed per runner per delivery

Speed = distance ÷ duration (in hours). Multiply duration in minutes by 60 to convert to km/h. Per-delivery breakdown lets you spot outliers — one runner had an unusually high speed on a specific order worth investigating.

SQL B6
SELECT
    runner_id,
    order_id,
    ROUND(AVG((distance / duration) * 60)) AS avg_speed_kmh
FROM runner_orders
WHERE duration <> 0
GROUP BY 1, 2
ORDER BY 1, 2;

B7 Successful delivery percentage per runner

CTE first computes success and fail counts per runner using conditional aggregation, then the outer query divides to get the percentage. Integer division is intentional — matches the expected output.

SQL B7
WITH delivery AS (
    SELECT
        runner_id,
        SUM(CASE WHEN duration > 0 THEN 1 ELSE 0 END) AS success,
        SUM(CASE WHEN duration = 0 THEN 1 ELSE 0 END) AS fail
    FROM runner_orders
    GROUP BY 1
)
SELECT
    runner_id,
    (success * 100 / (success + fail)) AS success_pct
FROM delivery;

Section C: Ingredient Optimisation

The hardest section — normalising comma-separated strings into rows, pivoting with regexp_split_to_table, and assembling dynamic order labels with STRING_AGG. Required two temp tables to make the data queryable at all.

C0 Data Cleaning First

Both pizza_recipes.toppings and customer_orders.extras/exclusions store comma-separated lists in a single column — the classic anti-pattern. To query them meaningfully, they need to be exploded into one-row-per-value using regexp_split_to_table.

SQL C0 — pivot recipes to long format
CREATE TEMP TABLE pizza_recipes AS (
    SELECT
        pizza_id,
        TRIM(regexp_split_to_table(toppings, ','))::INTEGER AS topping_id
    FROM pizza_recipes
);
SQL C0 — pivot extras & exclusions
CREATE TEMP TABLE customer_order AS (
    WITH cleaned AS (
        SELECT
            order_id, customer_id, pizza_id, order_time,
            NULLIF(NULLIF(TRIM(extras),    'null'), '') AS extra_clean,
            NULLIF(NULLIF(TRIM(exclusions), 'null'), '') AS exclusions_clean
        FROM customer_orders
    ),
    split_extras AS (
        SELECT
            *,
            TRIM(regexp_split_to_table(extra_clean,      ','))::INTEGER AS extra_topping_id,
            TRIM(regexp_split_to_table(exclusions_clean, ','))::INTEGER AS exclusion_topping_id
        FROM cleaned
    )
    SELECT * FROM split_extras
);

NULLIF(NULLIF(TRIM(col), 'null'), '') — this double-NULLIF chain is a clean idiom for normalising dirty text columns that mix blank strings, the word 'null', and real NULLs into a single consistent NULL before further processing.

C1 Standard ingredients per pizza

Once pizza_recipes is in long format (one row per topping), this is a straightforward three-table join to get topping names alongside pizza names.

SQL C1
SELECT
    pizza_name,
    t.topping_id,
    rec.topping_name
FROM pizza_names AS pizza
JOIN pizza_recipes AS t
    ON pizza.pizza_id = t.pizza_id
JOIN pizza_toppings AS rec
    ON t.topping_id = rec.topping_id
ORDER BY 1;

C2 Most commonly added extra

SQL C2
SELECT
    e.topping_id,
    topping_name,
    COUNT(e.topping_id) AS n_used
FROM extras AS e
JOIN pizza_toppings AS t
    ON e.topping_id = t.topping_id
GROUP BY 1, 2
ORDER BY 3 DESC
LIMIT 1;

C3 Most common exclusion

Same pattern as C2, querying the exclusions table instead.

SQL C3
SELECT
    e.topping_id,
    topping_name,
    COUNT(e.topping_id) AS n_used
FROM exclusions AS e
JOIN pizza_toppings AS t
    ON e.topping_id = t.topping_id
GROUP BY 1, 2
ORDER BY 3 DESC
LIMIT 1;

C4 Dynamic order item labels

The most complex query in the section. Goal: produce a string like "Meat Lovers - Exclude Cheese - Extra Bacon, Peppers" for each order row. The approach uses STRING_AGG to aggregate topping names per order, then concatenates with COALESCE to suppress empty clauses.

SQL C4
WITH base AS (
    SELECT
        ROW_NUMBER() OVER () AS record_id,
        order_id, pizza_id
    FROM customer_orders
),
split_orders AS (
    SELECT order_id, cust.pizza_id, pizza_name,
           extra_topping_id, exclusion_topping_id
    FROM customer_order AS cust
    JOIN pizza_names AS pizza
        ON cust.pizza_id = pizza.pizza_id
)
SELECT
    b.order_id,
    pn.pizza_name
        || COALESCE(' - Exclude ' || STRING_AGG(DISTINCT et.topping_name, ', '), '')
        || COALESCE(' - Extra '   || STRING_AGG(DISTINCT xt.topping_name, ', '), '')
        AS order_item
FROM base b
JOIN pizza_names pn ON pn.pizza_id = b.pizza_id
LEFT JOIN split_orders s
    ON s.order_id = b.order_id AND s.pizza_id = b.pizza_id
LEFT JOIN pizza_toppings et ON et.topping_id = s.exclusion_topping_id
LEFT JOIN pizza_toppings xt ON xt.topping_id = s.extra_topping_id
GROUP BY b.record_id, b.order_id, pn.pizza_name
ORDER BY b.order_id;

STRING_AGG(DISTINCT ..., ', ') + COALESCE(prefix || agg, '') — this combination is the standard way to build dynamic comma-separated labels in PostgreSQL. COALESCE suppresses the prefix entirely when there are no values, so you never get "Meat Lovers - Exclude " with a trailing empty clause.

Section D: Pricing & Ratings

5 questions on revenue calculation, surcharge logic, schema design, and net profit after runner costs. This section combines conditional aggregation with multi-CTE arithmetic — and includes a schema design question that has no single right answer.

D1 Total revenue — no delivery fees, no extras charge

Fixed prices: Meatlovers = $12, Vegetarian = $10. Join to get the pizza name, filter to delivered orders only (distance != 0), and use CASE WHEN inside SUM to apply the right price per row.

SQL D1
SELECT
    SUM(CASE WHEN pizza_name = 'Meatlovers' THEN 12 ELSE 10 END) AS total_revenue
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
JOIN pizza_names AS pizza
    ON cust.pizza_id = pizza.pizza_id
WHERE distance != 0;
total_revenue
$138

D2 Revenue with $1 surcharge per extra topping

Now extras cost $1 each. The trick is counting the number of items in the comma-separated extras string — array_length(string_to_array(extras, ','), 1) gives the count. The NULLIF chain first normalises empty/null extras to NULL so they don't get counted.

SQL D2
WITH orders AS (
    SELECT
        CASE WHEN pizza_name = 'Meatlovers' THEN 12 ELSE 10 END AS base_price,
        CASE
            WHEN NULLIF(NULLIF(TRIM(cust.extras), 'null'), '') IS NULL
                THEN 0
            ELSE array_length(string_to_array(cust.extras, ','), 1)
        END AS extras_surcharge
    FROM customer_orders AS cust
    JOIN runner_orders AS runna
        ON cust.order_id = runna.order_id
    JOIN pizza_names AS pizza
        ON cust.pizza_id = pizza.pizza_id
    WHERE distance != 0
)
SELECT SUM(base_price + extras_surcharge) AS total_revenue
FROM orders;

array_length(string_to_array(col, ','), 1) — the cleanest way to count comma-separated items in PostgreSQL without exploding rows. string_to_array splits the string into an array; array_length(..., 1) returns the length of the first dimension.

D3 Design a runner ratings table

This is a schema design question — there's no single right answer, but the key constraints are: one rating per successful order, rating between 1 and 5, and it should join cleanly to runner_orders on order_id.

SQL D3 — schema + sample data
CREATE TABLE runner_ratings (
    rating_id     SERIAL        PRIMARY KEY,
    order_id      INTEGER       NOT NULL,
    runner_id     INTEGER       NOT NULL,
    customer_id   INTEGER       NOT NULL,
    rating        INTEGER       NOT NULL CHECK (rating BETWEEN 1 AND 5),
    rated_at      TIMESTAMP     DEFAULT NOW()
);

-- Sample ratings for successful deliveries

D4 Full delivery summary table

Join everything together: customer info, runner info, rating, timing, speed, and pizza count per order — one row per successful delivery.

SQL D4
SELECT
    cust.customer_id,
    cust.order_id,
    runna.runner_id,
    rr.rating,
    cust.order_time,
    runna.pickup_time,
    ROUND(EXTRACT(EPOCH FROM
        (runna.pickup_time::timestamp - cust.order_time::timestamp)
    ) / 60)                                        AS mins_to_pickup,
    runna.duration                                   AS delivery_duration_mins,
    ROUND((runna.distance / runna.duration) * 60)   AS avg_speed_kmh,
    COUNT(cust.pizza_id)                             AS total_pizzas
FROM customer_orders AS cust
JOIN runner_orders AS runna
    ON cust.order_id = runna.order_id
JOIN runner_ratings AS rr
    ON cust.order_id = rr.order_id
WHERE runna.distance != 0
GROUP BY
    cust.customer_id, cust.order_id, runna.runner_id,
    rr.rating, cust.order_time, runna.pickup_time,
    runna.duration, runna.distance
ORDER BY cust.order_id;

Why GROUP BY here? Each order can have multiple pizzas in customer_orders, so without grouping, joining to the single-row runner_orders and runner_ratings tables would produce duplicate rows per pizza. GROUP BY collapses them and lets COUNT(pizza_id) give the correct total per order.

D5 Net profit after runner costs

Runners are paid $0.30/km. Two CTEs compute total revenue and total runner costs independently, then the outer query subtracts them. Keeping revenue and costs in separate CTEs makes the logic easy to audit and change.

SQL D5
WITH revenue AS (
    SELECT
        SUM(CASE WHEN pizza_name = 'Meatlovers' THEN 12 ELSE 10 END) AS total_revenue
    FROM customer_orders AS cust
    JOIN runner_orders  AS runna ON cust.order_id = runna.order_id
    JOIN pizza_names    AS pizza ON cust.pizza_id  = pizza.pizza_id
    WHERE distance != 0
),
costs AS (
    SELECT
        SUM(distance * 0.3) AS runner_costs
    FROM runner_orders
    WHERE distance != 0
)
SELECT
    total_revenue                       AS gross_revenue,
    runner_costs                        AS total_runner_costs,
    total_revenue - runner_costs        AS net_profit
FROM revenue, costs;

Multi-CTE arithmetic — separating revenue and cost into their own CTEs keeps each calculation independently testable. You can run either CTE alone to verify it before combining. This pattern scales cleanly when you add more cost/revenue lines later.

What This Case Study Tests

Pizza Runner is genuinely harder than Danny's Diner — not because the questions are more complex in isolation, but because the data is intentionally messy. Before you can answer anything meaningfully you have to fix it. That's closer to real work than most SQL challenges.

Across all four sections the key skills are: dirty data diagnosis (spotting the 'null' string vs SQL NULL problem), datetime arithmetic with EXTRACT(EPOCH FROM ...), string normalisation using regexp_split_to_table and STRING_AGG, and multi-CTE financial modelling for clean revenue/cost separation.
