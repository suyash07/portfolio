SQL From First Principles

The Setup

Danny's Diner is a small Japanese restaurant with three items on the menu - sushi, curry, and ramen. Danny wants to understand his customers: who visits most, what they order, how the loyalty program is performing, and whether it's actually worth running.

The schema is intentionally minimal - three tables (sales, menu, members) - but the questions get surprisingly layered quickly. That's what makes this case study a good benchmark: simple data, non-trivial logic.

Why this matters beyond the challenge: These exact patterns - joining on inequality conditions, ranking within groups, conditional point systems - show up constantly in real production work. I use variations of Q6 and Q10 logic weekly in financial model monitoring at Zions.

1 Total Amount Each Customer Spent

The straightforward read: join sales to menu on product_id, sum the price per customer. One join, one aggregate.

SQL Question 1
SELECT
    s.customer_id,
    SUM(m.price) AS total_spent
FROM sales AS s
JOIN menu AS m
    ON s.product_id = m.product_id
GROUP BY s.customer_id
ORDER BY s.customer_id;

Customer A leads narrowly over B; C is well behind. Already you can see why a loyalty program targeting A and B makes sense.

2 How Many Days Did Each Customer Visit?

The key here is DISTINCT order_date - a customer can place multiple orders on the same day and we want to count that as one visit.

SQL Question 2
SELECT
    customer_id,
    COUNT(DISTINCT order_date) AS times_visited
FROM sales
GROUP BY customer_id;
customer_idtimes_visited
A4
B6
C2

B visits most frequently despite spending almost the same as A - meaning B spends less per visit. C is a very infrequent customer.

3 First Item Purchased by Each Customer

This is the first window function problem. We rank each customer's orders by date and pull rank = 1. I used ROW_NUMBER() here - if two orders share the earliest date, this picks one arbitrarily. DENSE_RANK() would surface both ties.

SQL Question 3
WITH rnk AS (
    SELECT
        *,
        ROW_NUMBER() OVER(
            PARTITION BY customer_id
            ORDER BY order_date
        ) AS rnk
    FROM sales
)
SELECT
    rn.customer_id,
    m.product_name
FROM rnk AS rn
JOIN menu AS m
    ON rn.product_id = m.product_id
WHERE rnk = 1;

Window function pattern: ROW_NUMBER() OVER(PARTITION BY ... ORDER BY ...) is one of the most reusable patterns in analytical SQL. Any time you need "the first/last X per group," this is your tool.

4 Most Purchased Item Overall

Simple count-and-rank. Join to get the product name, group and count, sort descending, take the top row.

SQL Question 4
SELECT
    s.product_id,
    m.product_name,
    COUNT(s.product_id) AS purchase_count
FROM sales AS s
JOIN menu AS m
    ON s.product_id = m.product_id
GROUP BY 1, 2
ORDER BY 3 DESC
LIMIT 1;

Ramen is the most purchased item - which also informs the loyalty program design in Q9 and Q10.

5 Most Popular Item Per Customer

Now we want the favourite per customer, not overall. This calls for RANK() rather than ROW_NUMBER() - if a customer ordered two items equally often, we want both to show up (rank 1 tie), not just one.

SQL Question 5
WITH cte AS (
    SELECT
        customer_id,
        product_id,
        COUNT(product_id) AS product_freq,
        RANK() OVER(
            PARTITION BY customer_id
            ORDER BY COUNT(product_id) DESC
        ) AS rnk
    FROM sales
    GROUP BY 1, 2
)
SELECT
    c.customer_id,
    m.product_name
FROM cte AS c
JOIN menu AS m
    ON c.product_id = m.product_id
WHERE rnk = 1;

ROW_NUMBER vs RANK vs DENSE_RANK: Use ROW_NUMBER when you want exactly one result per group. Use RANK when ties should both surface and gaps in rank are acceptable. Use DENSE_RANK when ties should surface with no gaps.

6 First Purchase After Becoming a Member

This is where the members table comes in. The join condition is the key - we filter to orders on or after the join date using an inequality in the ON clause, then rank within each customer to find their first post-membership order.

SQL Question 6
WITH cte AS (
    SELECT
        s.*,
        menn.product_name,
        RANK() OVER(
            PARTITION BY s.customer_id
            ORDER BY order_date
        ) AS rnk
    FROM sales AS s
    JOIN members AS m
        ON s.customer_id = m.customer_id
        AND s.order_date >= m.join_date
    JOIN menu AS menn
        ON s.product_id = menn.product_id
)
SELECT customer_id, product_name
FROM cte
WHERE rnk = 1;

The inequality join (order_date >= join_date) is a pattern I find comes up constantly in financial work - filtering events to a specific time window relative to a reference date per entity.

7 Last Purchase Before Becoming a Member

Same structure as Q6 but flipped: orders before join date, ranked in reverse (ORDER BY order_date DESC) so rank 1 = the most recent pre-membership order.

SQL Question 7
WITH cte AS (
    SELECT
        s.*,
        menn.product_name,
        join_date,
        RANK() OVER(
            PARTITION BY s.customer_id
            ORDER BY order_date DESC
        ) AS rnk
    FROM sales AS s
    JOIN members AS m
        ON s.customer_id = m.customer_id
        AND s.order_date < m.join_date
    JOIN menu AS menn
        ON s.product_id = menn.product_id
)
SELECT customer_id, product_name
FROM cte
WHERE rnk = 1;

8 Total Items and Spend Before Membership

Aggregate version of Q7 - instead of finding the last item, we want the total count and spend across all pre-membership orders. No window function needed; a straight aggregation after the filtered join does it.

SQL Question 8
SELECT
    s.customer_id,
    COUNT(s.product_id)  AS total_items,
    SUM(menn.price)      AS total_spent
FROM sales AS s
JOIN members AS m
    ON s.customer_id = m.customer_id
    AND s.order_date < m.join_date
JOIN menu AS menn
    ON s.product_id = menn.product_id
GROUP BY 1;

9 Points Calculation - Sushi 2× Multiplier

Here's where CASE WHEN inside an aggregate becomes essential. The rule: $1 = 10 points, sushi = 2× multiplier. The CASE evaluates per row before SUM collapses them.

SQL Question 9
SELECT
    s.customer_id,
    SUM(
        CASE
            WHEN product_name = 'sushi'
                THEN price * 10 * 2
            ELSE price * 10
        END
    ) AS total_points
FROM sales AS s
JOIN menu AS m
    ON s.product_id = m.product_id
GROUP BY 1;

Pattern to remember: SUM(CASE WHEN ... THEN ... ELSE ... END) is conditional aggregation. It's the SQL equivalent of a weighted sum - you'll reach for this constantly in any analytics or reporting context.

10 First-Week Bonus Points in January

This is the most layered question. In the first 7 days after joining, everything earns 2× (not just sushi). Outside that window, normal rules apply. And we only count January orders.

Three nested conditions in the CASE: first-week window → sushi anywhere else → everything else. The join filters to post-membership orders only, and the WHERE clause bounds to January.

SQL Question 10
SELECT
    s.customer_id,
    SUM(
        CASE
            -- First 7 days after joining: 2x on everything
            WHEN s.order_date BETWEEN m.join_date
                                      AND m.join_date + 6
                THEN menn.price * 10 * 2
            -- Outside first week: sushi still 2x
            WHEN menn.product_name = 'sushi'
                THEN menn.price * 10 * 2
            -- Everything else: standard 10 pts per $
            ELSE menn.price * 10
        END
    ) AS total_points
FROM sales AS s
JOIN members AS m
    ON s.customer_id = m.customer_id
    AND s.order_date >= m.join_date
JOIN menu AS menn
    ON s.product_id = menn.product_id
WHERE
    order_date - join_date <= 7
    AND order_date <= '2021-01-31'
GROUP BY 1;

Order of CASE matters. SQL evaluates CASE conditions top to bottom and stops at the first match. The first-week check has to come before the sushi check - otherwise a sushi order in the first week would match the sushi branch (2×) instead of the first-week branch (also 2×, but by the right rule). In this case the result is the same, but getting the logic order right matters when multipliers differ.

Key Patterns from This Challenge

Working through all 10 questions, a small set of patterns accounts for almost every solution:

CTE + window function: Filter to a group's first/last row. Used in Q3, Q5, Q6, Q7. The template is always the same - rank in a CTE, filter on rank = 1 in the outer query.

Inequality join: Joining two tables where the match condition is a range, not equality. order_date >= join_date in Q6–Q8. This is how you attach a time-dependent reference point (membership date, loan origination, pricing effective date) to event-level data.

Conditional aggregation: SUM(CASE WHEN ... THEN ... END) in Q9 and Q10. Any time your metric has multiple rules depending on a row attribute, this is the right tool - not separate queries per segment.

These three patterns together cover the vast majority of real analytical SQL work. Master them here, and you'll recognize them instantly in production contexts.
